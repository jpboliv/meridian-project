Meridian · Incident response case study

When should an incident agent restart a service?

Orders are slow to reach a simulated stock exchange. The last time this happened, one gateway instance ran low on memory. This time, the database link could be slow. What evidence does the on-call agent need before it acts? And if it stops halfway through a restart, how does the next worker know what happened?

M1 · Decide from current evidence

In case A, only instance 2 showed high memory use. Both links were healthy. The agent obtained approval, restarted that instance, and confirmed recovery with three consecutive readings. In B, the monitor timed out twice on instance 1. Instance 2 was never measured. The useful outcome was a handoff: get readings for both instances, restart neither.

The live model baseline passed 9 of 15 runs on m1.6. On m1.7, all five scripted cases passed. Those five cases test the decision rules. They do not establish that the model improved.

M2 · Is yesterday’s clue worth carrying forward?

In C, the fault moved to instance 1. The model received the full runbook either with or without a reminder from the previous shift. In the three pairs where it saw the reminder, it made the same six reads in the same order and restarted the right instance either way. All 12 runs passed. The runbook alone remains the default.

A separate 45-run study varied the position of the timestamp and compared automatic caching with caching off. All runs passed. The 157 requests contained 571 to 803 input tokens each, below the provider’s 1,024-token minimum. With no cache reads or writes, the study could not measure savings from reuse.

M3 · Resume the investigation without restarting twice

Two scripted specialists investigated the application and infrastructure. In A and D, the team reached the same decision as the single agent with one extra tool call per case. When the application specialist did not reply, the lead told the operator which evidence was missing.

In the interruption test, the worker stopped after the restart but before it saved the receipt. The simulator kept running. The replacement found the original receipt, ACT-001, and confirmed recovery from three fresh readings. There was one restart. When the link degraded instead, the same receipt led to a handoff, not a claim of recovery.
