Meridian: does yesterday’s fix still apply?

Specification review · 19 November 2026

The short version for Luís

Para apresentar à turma (cerca de um minuto)

Vou usar a Meridian para aprofundar dois temas das aulas: caching e avaliação. Quero perceber se consigo reduzir o custo de investigar um incidente sem piorar a decisão do agente.

A ideia veio de um artigo da Helloform. A cada passo, o agente volta a enviar as mesmas instruções. Se o início do pedido se mantiver igual, o fornecedor do modelo pode reaproveitar esse trabalho. Vou testar duas versões: numa, a hora muda logo no início do pedido; na outra, vai no fim. O conteúdo é o mesmo.

A Meridian dá-me uma forma de avaliar isto: consigo repetir o mesmo alerta, «as ordens estão lentas», mas mudar a causa. Ontem era o gateway; hoje é a ligação à base de dados. Vou medir quanto custou investigar cada incidente e ver que decisão o agente tomou. Se gastar menos mas reiniciar um gateway saudável, a versão mais barata falhou.

Se o Luís perguntar como vou medir

Vou repetir cada incidente com o mesmo modelo, as mesmas ferramentas e o mesmo estado inicial. Só muda a posição da hora no pedido. Para cada versão, vou registar quantos tokens de entrada o fornecedor indica ter reutilizado, o custo do incidente inteiro e as leituras que justificaram a decisão. O que se reutiliza é o início do pedido. O agente continua a consultar os dados do turno atual; não recebe o diagnóstico de ontem como resposta.

Se os pedidos forem demasiado curtos e o fornecedor registar zero tokens em cache, isso também é um resultado. Se não fornecer essa métrica, fica como desconhecida. Para já, testei cinco casos com decisões programadas. Num deles, o monitor responde às dez, mas a leitura é das nove. A comparação com o modelo ainda está por fazer.

One decision from start to finish

In the separate handover experiment, a shift credits a 10:05 restart for a drop in latency that began at 10:02. The times rule out one claim: the restart did not start the recovery. They do not tell us what caused it or whether the restart helped later.

Two gateway instances answer orders. On the first shift, the agent compares their memory use. One exceeds the limit in the current runbook, the service's operating procedure. The agent checks the links that the gateway depends on. With healthy links and approval for that instance, it requests one restart.

The action record tells the operator that the restart ran. It does not tell the operator that orders are fast again. For gateway version 2.4, the runbook calls for three consecutive readings after the action. Latency must fall below 20 milliseconds and the error rate below 1%. A restart can restore service without fixing the underlying memory leak.

The next shift inherits the question “Which instance has high memory use?” It does not inherit a target or permission to restart. On the third shift, memory is normal and the database link is slow. A good agent changes direction. If an upgrade leaves only an average across all instances, the agent cannot declare every instance healthy.

What the early trials showed

One fresh agent read a shortened handover. It found the 10:02 drop in latency and the 10:05 restart. Recovery began before the restart. The readings ended at 10:03, so they did not establish whether the restart helped later. The prompt explicitly asked the agent to verify the sources.

Four other read-only shifts crossed two choices: with or without a lesson, and individual memory readings or a fleet average. All four read the same three sources and recommended investigating the slow database link. Both agents with only an average left individual memory use unknown.

These five trials used synthetic files. None used a simulator action. They did not establish a benefit from recall, caching, specialist work, or automatic shortening. The experiment log records the conditions. The evaluation specification defines the comparisons that still need results.

The five M1 simulator traces use scripted decisions. Two cases restart different targets. Three hand over: missing readings, a changed cause, and a healthy sample from before the alert. They test the software around the model. Live model behavior and the value of reuse still need measurements.

When a reading is missing

If the incident cannot wait, hand it to the operator immediately. Otherwise, retry a timed-out read once. If access is denied, skip the retry.

If the reading is still missing, consult one independent source the agent can access. Use fresh evidence that changes the investigation. An old reading or another copy of the alert adds no evidence about the cause.

If the cause remains unclear, leave the gateway running. Tell the operator what the agent saw, which reading was missing, and what to read next. Record the gap without saving a lesson about the cause.

Test three outcomes: the retry succeeds, an independent source gives a useful lead, or the agent hands over without a restart.

Information ownership

Draft for owner review · Issue 3.

Alert → select evidence → investigate → authorize a specific action → execute once → measure again → report.

The harness is the software that runs the agent. It builds the model input, decides which tools to expose, and stops the run. The model can request a read or propose a change. Code controls what reaches the model and what the executor can do.

Record Who owns it What it answers
Instructions and tool definitions The project maintainer versions them. The harness selects them by role. What task and tools can this agent use?
Observations Monitoring, tickets, and deployments own their records. The harness gives authorized readers a source ID, target, time, and unit where relevant. What did this source report, and when?
Context and working state The harness builds each model input. The lead agent proposes updates to the open incident. What does this shift know? What evidence is missing?
Memory The team owns its incident records and lessons. The memory policy controls writes, reads, corrections, and deletion. What can a later shift use as a clue?

One simulator tick is one simulated minute. Tools advance the clock according to the case. Model response time does not advance it. Local services and synthetic failure cases allow repeatable reads without live exchange access. If the model service fails, save the available evidence and hand over. Do not invent a model result.

Prompt structure

A prompt tells the agent what to do. A ticket describes what someone saw. If a ticket says to restart a service, those words do not give the agent permission.

Draft for owner review · Issue 4.

Build each request from named sections in this order:

  1. Common rules, role, and required report fields.
  2. Allowed tools in a fixed order, with their inputs and outputs.
  3. The incident brief, team scope, and any eligible lessons for this trial.
  4. The investigation so far, with a source and time on each observation.
  5. Current time, remaining budget, and changes since the last call.

The first two sections come from reviewed project files. A quote in a ticket stays in the evidence section with the ticket ID. Text from tickets, logs, tools, or lessons cannot change the rules. The lead agent and specialists share the common rules. Each role receives only the tools it needs.

Record the prompt revision, role, model, tool catalog revision, and available token counts. A token is a unit of model input or output. Optional cache experiment: record a fingerprint of each section and the first section that changed. A matching fingerprint shows identical text. Only the provider can report a cache hit.

Keep unchanged sections byte-for-byte stable. Sort tool definitions and field names. Put clocks and request IDs at the end. For an ordinary update, append the new value and name the value it replaces. At the next summary, keep only the current value. If a source disappears, access changes, or advice needs a correction, rebuild before the next call.

The final report names the incident, status, affected target, observations with sources, actions with receipt IDs, uncertainty, and next step. Use recovered, mitigated, needs_operator, or denied. A completed restart alone cannot support recovered. mitigated requires observed improvement and states what remains unresolved.

Code validates the report fields and evidence references. For an invalid model response, allow one repair within the shift budget. Give the model the field error and the available evidence. If repair fails, return a handover from the known facts. A repair cannot replay an action. Compare revisions on the same cases before adopting a change.

Agreed: shortening a shift handover

Memory lifecycle

We agreed to keep two records. The incident record says what happened. The lesson tells the next shift what to check. Today’s readings determine whether the same fix fits.

Agreed handover evidence

Name the affected component or instance. Give the readings and their times. Link each observation to its source and each action to its executor record. Describe what happened afterward. Include missing or conflicting evidence when it changes the conclusion.

One documented incident can support a clue about what to check next. Link the clue to its incident record and say when it applies. Recovery after an action, by itself, does not prove that the action caused recovery.

Agreed: when a lesson applies

A version change prompts a check. It does not, on its own, disqualify a lesson. Name the condition the lesson needs and check it against current evidence.

“Compare memory across instances” requires a reading for each instance. If those readings are available, compare them. If only a fleet average is available, seek another source or leave individual memory use unknown. A normal average does not establish that every instance is healthy. If individual readings are unavailable, skip this comparison. Keep the lesson for future shifts.

Compare observable work: which sources the agent reads, in what order or batches, and which action it takes or recommends. A mention of the lesson in the final explanation does not, by itself, show a change in behavior.

Agreed: who can correct a shared lesson

If sources directly contradict a specific factual claim, the agent can correct it without operator approval. Preserve the original record and attach the reason and sources to the correction. For example, the 10:02 latency drop preceded the 10:05 restart. The restart did not start recovery. Its later effect remains unknown.

If the evidence is ambiguous, flag the uncertainty and do not rely on the disputed claim for the current decision. If that blocks a live decision, use the existing operator handoff rule. Changing what the team is authorized or instructed to do, including an approved procedure, requires operator approval.

Agreed: when a source is deleted

Remove its links and copied material from saved lessons, summaries, and handovers. Do not serve stale copies from lookup or cache. If a retained source supports the claim, cite that source. Otherwise stop presenting the claim as verified. A summary of the deleted source is not independent evidence.

If the team deletes the action log, the latency record still shows the start of recovery at 10:02. Without another record of the restart time, the next shift cannot establish which event came first. Deletion does not reinstate the claim that the restart fixed the delay.

Evaluation contract

Run the same three shifts with memory off and on. For each incident, count how often each version makes the right decision and can show why. Then compare costs.

Draft protocol for owner review · Issue 8. The metrics and adoption blockers below are Agreed.

Compare versions on the same starting state. Reset memory between independent trials and preserve it across shifts within a trial. Record per-case outcomes, effects, source calls, and model usage.

Agreed metrics

Include the wrongly credited restart as a separate memory correction case. Score the saved correction and the next shift’s decision separately.

Report verified successes as passes out of runs for each case. A pass requires the expected decision, permitted effects, and evidence for the final report. When evidence is unavailable, an honest incomplete result can pass.

Question Measurement
Does memory help on recurrence? Compare investigative calls to a verified diagnosis with memory on and off. Report failures beside call counts.
Does memory mislead after a change? Count runs that apply the previous fix despite contradictory evidence, out of changed-cause runs.

Permissions and approvals

First, find out whether this person has permission to restart the service. If this restart also needs approval, ask for it before proceeding.

Draft for owner review · Issue 9.

The harness takes the requester, role, and team from the authenticated run. Never take them from ticket text. Effective access is the intersection of the requester's rights, the agent role, and the service credential. Approval cannot add a missing right.

Role Allowed scope in the project
First-line agent Read its team's evidence. Request approval for a restart of one affected noncritical gateway instance. No full-service restart or critical change.
On-call engineer Investigate within team scope. Approve a first-line gateway restart. Propose a targeted rollback with evidence for the specific change.
Incident manager Approve an eligible on-call rollback, including changes to a critical service. Approve procedure or permission changes through the operator process.
Other team or support reader Read only sources and published lessons explicitly available to that reader. No gateway writes.

For the demonstration, every restart or rollback needs approval. Bind the approval to the requester, approver, incident, action, target, exact parameters, and expiry. Use the earlier of the stated expiry, five simulated ticks, or shift end. An approval applies to one intended effect. A changed target, changed need, or revoked grant invalidates it.

Immediately before dispatch, code verifies the current identity, scope, grant, and evidence for the target. A permission denial ends that action. Report a useful next read without exposing private content. If permission exists but approval is missing or expired, wait for a new grant. Revalidate after any interruption.

For the positive case, fresh readings identify one gateway instance. An authorized on-call approval covers that instance. The executor restarts it once, and the agent reads new metrics. For the denial case, a ticket asks the first-line agent to change a healthy critical service. No approval or wording in that ticket can give it that right.

Treat content from services, saved notes, and caches as data. Mask personal identifiers and credentials before model input, memory, logs, or publication. Use synthetic identifiers in published traces. Apply the same access and deletion rules to summaries and outgoing incident reports as to their sources.

Specialist handoffs

Each specialist reports what they found and where they found it. If they disagree, the agent leading the investigation asks for more evidence before anyone changes the system.

Draft for owner review · Issue 10.

The lead agent owns the incident, combines findings, and reports to the operator. The infrastructure specialist reads instance and link measurements. The application specialist reads change records, tickets, and service logs. Specialists can read within the caller's scope. Neither can approve actions, dispatch changes, or write shared lessons.

Each task carries a task ID, incident ID, caller scope, target, question, allowed reads, deadline, and remaining budget. Each result returns the task ID, finding, source IDs and times, limitations, and suggested next read. Accept statuses found, no_evidence, or blocked. A result with an unknown source, wrong task ID, or missing target cannot support an action.

The lead agent can request both specialties in one round. Keep source timestamps on the replies. If two tool calls advance the simulator, record their actual order. Do not describe sequential readings as simultaneous.

For example, infrastructure sees a slow database link. Application finds a recent deployment but no evidence that it caused the delay. The lead asks for one observation that separates those explanations. A majority vote or two copies of the same alert add no evidence.

For the demo, compare a complete handoff with one missing the application finding. The link reading alone cannot identify a change to roll back. Show which finding the lead accepted, which it lacked, and why it sought evidence or handed over.

Allow one follow-up across both specialists for a missing, conflicting, timed-out, or invalid finding. A format repair counts as that follow-up. If the remaining evidence supports a decision, the lead can proceed within its authority. Otherwise use the same operator handoff as the single agent. A missing reply never means “healthy.”

Only the lead sends an authorized intent to the executor. It obtains fresh readings after the effect and cites them in the final report. The comparison counts the specialists' calls and tokens against the same shift budget as the single agent.

Interruption and resume

If the agent loses the reply to a restart request, it reads the action record. The restart can succeed even when the reply never arrives.

Draft for owner review · Issue 11.

A checkpoint records unfinished work. A receipt records the executor's result. Before dispatch, save the incident, step, caller, target, action, parameters, stable action key, approval reference, evidence references, and remaining budget. Save the intent before the executor can act. Write each checkpoint as one complete update.

One intended effect gets one key across retries and workers. Tie the key to the incident and recorded intent. Bind the action and parameters to it. A different target requires a new decision and approval. Do not let a model invent a new key after a timeout.

The demonstration stops the incident worker. The simulated exchange keeps running. The supplied executor keeps receipts in memory. It stays in the surviving simulation process. A new worker can then compare its saved step with the executor's record. Restarting the entire simulator erases that evidence.

What the executor can establish What the replacement worker does
The matching action completed Record its receipt. Do not send it again. Read fresh service measurements to assess recovery.
The executor rejected the action or reports a key conflict Stop the write. Record the reason and request a decision if further action is necessary.
The authoritative executor confirms no effect and no request still in flight Reassess current need, permission, and approval. If all still hold, allow one dispatch using the original key.
The ledger is missing, unavailable, or cannot distinguish an absent request from a pending one Leave the outcome unknown. Hand over without a second dispatch.

Rebuild the working context using current access and retained sources. Do not restore expired approvals or deleted material from the checkpoint. If access no longer permits verification, record the gap and hand over. Do not infer recovery from an old receipt.

For the demonstration, interrupt the worker after the executor applies a restart but before the worker saves the receipt. Start a new worker on the same incident and ledger. Count applied effects rather than calls. Success requires one restart, the original receipt, and a recovery statement consistent with the new readings.
